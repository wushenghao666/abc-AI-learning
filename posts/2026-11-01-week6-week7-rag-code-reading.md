前两周把问答链和页面做了出来，也部署到了 GitHub Pages 和 Render。这次没有继续加功能，而是先把两条视频线索补完，再把 week 6 目录里的代码从头读一遍：哪些函数现在真的在跑，哪些已经没人调用，简化的时候又丢掉了什么。

读下来发现三个具体问题。问“第四周怎样实现会话恢复”，检索结果的第一名是第五周博客；34 项自动测试因为一个已经不存在的函数名，直接导入失败，一项都没执行；README 里写的部署工作流和接口，也和现在的代码对不上。下面先写学习，再写项目，最后写这三个问题。

## 学习部分

### RAG 工作机制：把六个环节对到代码上

[马克的技术工作坊：RAG 工作机制详解](https://www.bilibili.com/video/BV1JLN2z4EZQ)把知识库问答拆成资料解析、切分、索引、检索、上下文组织和生成回答。这次边看边把项目和它逐段对上，正好一个环节对应一处代码：

| 视频里的环节 | 项目里的实现 | 实际参数 |
| --- | --- | --- |
| 资料解析 | `build_index()` 逐个读取 `data/raw/` 的十份快照 | `import_sources()` 只确认快照存在 |
| 切分 | `split_markdown()` 先按标题，再按窗口 | 700 字符，不重叠，105 段 |
| 索引 | `build_index()` 写 `simple-index.json` | 纯 JSON，没有向量 |
| 检索 | `retrieve()` 关键词重合计数排序 | k 默认 4，上限 8 |
| 上下文 | `prompt()` 拼编号、文件、章节和原文 | 每条命中带一个 `[n]` |
| 生成 | `answer()` 调兼容 Chat Completions 的接口 | temperature=0 |

视频里有两个说法这次体会比较深。第一，检索回来的片段必须能回到原文核对，回答“看起来对”不算数。所以页面上除了回答，还留着来源文件和章节，结论后面跟着编号。第二，切分窗口的大小和是否重叠，会同时影响命中情况和送进模型的上下文长度。上一版用 480 字符、重叠 80，把周次和标题一起编码；现在这版为了读起来简单，改成 700 字符、不重叠，也不再拼接额外字段。项目部分会看到这个改动带来的后果。

### LangChain 前 27 集：先手写一遍，再换抽象

第二条线索是[黑马程序员 2026 最新版 LangChain](https://www.bilibili.com/video/BV178w1z7EHQ)的前 27 集。这 27 集的内容大致分四层：模型调用和提示模板；输出解析和链式调用；文档加载、切分、检索；工具和 Agent。

对照自己手写的代码，其实每个角色都在，只是没有框架的统一接口：

- 文档加载对应 `build_index()` 里读快照的那几行，`import_sources()` 只负责确认快照存在，不做递归扫描；
- 文本切分对应 `split_markdown()`，按 Markdown 标题断开；
- Retriever 对应 `retrieve()`，现在是关键词重合排序；
- PromptTemplate 对应 `prompt()`，把资料拼成带编号的文本；
- ChatModel 对应 `answer()`，发一个 `chat/completions` 请求；
- OutputParser 的位置，上一版由 `generation.py` 的 JSON 结构和引用校验承担，这一版还没有。

看完这几层的分工，我更能接受“先手写、后换框架”的顺序。手写一遍知道每一步的输入输出是什么，换的时候才知道框架替自己做了什么。反过来，一上手就用 Runnable 组装，出错时很难判断是提示、检索还是解析的问题。下一步我打算只替换一层，比如把 `retrieve()` 换成一个 LangChain Retriever，其余保持手写，用同一组问题比较排序结果，而不是整套搬进来。

## 项目部分

### 现在的结构：两条路径

项目里其实有两套实现。一套是能读完的最小链路，一套是上一版的完整实验平台。当前入口是前者，后者留在仓库里当实验记录：

| 模块 | 职责 | 现在谁在用 |
| --- | --- | --- |
| `src/simple_rag.py` | 读取、切分、检索、提示、模型调用 | `cli.py`、`web.py`，约 150 行 |
| `src/web.py` + `web/` | HTTP 服务、页面与示例 | 本地和线上入口 |
| `src/corpus.py`、`embeddings.py`、`retrieval.py` | 白名单导入、BGE 向量、BM25 与 RRF 组合 | 只有评估与审计脚本 |
| `src/generation.py`、`service.py` | 编号原文单元、引用校验、过程事件 | 只有评估与审计脚本 |
| `evaluation/`、`reports/`、`tests/` | 24 道固定题、实验记录、自动测试 | 评估与回归 |

简版的好处是能一口气读完：150 行，十个函数，没有向量、没有依赖注入，也没有流式接口。代价是上一版为了“可核对”加的东西基本都没了。

### 最小链路具体在做什么

一次请求走四步：按 `week*-*.md` 读取十份快照，按 Markdown 标题和 700 字符窗口切段；把问题和片段都拆成英文数字词加中文双字词，按词集合重合数量排序取前 k 段；把命中的片段编成 `[1]`、`[2]` 这样的上下文；最后要么只返回片段，要么把问题和上下文发给模型。默认勾选“只检索”，取消勾选才会真正请求模型；没有配置密钥时直接返回 `retrieval_only`，不会伪造回答。

和上一版放在一起，差异就很清楚：

| 环节 | 当前最小链路 | 上一版完整链路 |
| --- | --- | --- |
| 切分 | 700 字符，不重叠 | 480 字符，重叠 80，优先段落与句末 |
| 片段数 | 105 | 112 |
| 检索 | 关键词重合计数 | BM25、BGE 向量、RRF 组合三选一 |
| 引用 | `[n]` 加文件与章节 | source/span 编号，取回未经改写的原文 |
| 校验 | 无 | 结构、编号、逐字匹配三道 |
| 测试 | 34 项，当前导入失败 | 34 项，曾记录为全部通过 |

片段数从 112 降到 105，不是因为资料变少，而是窗口变大、不再重叠。这也解释了为什么后面检索会变糙：同样的内容被切成更少的、更长的段，一段里混进了更多主题。

### 问题一：检索把第五周排在第四周前面

用页面上第一个示例提问：

```text
问题：第四周怎样实现会话恢复？
第一名：week5-blog.md ｜ 章节「资料」｜ 重合分数 5
```

第一名不是第四周博客，而是第五周博客开头的一段。原因有两层。第一，`split_markdown()` 只跳过 `---` 这一行，没有跳过 front matter 本身，所以 `title:`、`date:`、`tags:`、`excerpt:` 都被当成正文切进片段，章节名还统一叫“资料”。第二，第五周的 excerpt 里写着“延续第四周的持久化 Agent”，其中“第四周”正好命中问题，于是这条元数据靠一次词面重合排到了真正的实现说明前面。

上一版没有这个问题：`sections()` 从 front matter 之后开始切，`indexed_text()` 还会把“第 N 周 标题”拼进参与检索的文本，周次因此不是噪音而是信号。

修改方向不难，但要重测：切分时跳过 front matter；把周次和标题拼回索引文本；如果还想更稳，可以给元数据字段降权。这三步都会改变排序，需要重跑同一组 24 题才能说清楚是变好还是变坏。

### 问题二：34 项测试一项都没跑起来

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
# ImportError: cannot import name 'handler_for' from 'src.web'
```

`tests/test_rag.py` 测的是上一版的 HTTP 层：流式过程事件、跨域拒绝、路径穿越、请求体上限，这些都以 `src.web.handler_for()` 返回的处理器为入口。简化时 `web.py` 被整个换掉，不再提供这个函数，测试文件在导入阶段就失败，34 个用例一个都不会执行。

也就是说，这次能看出来的只有“测试跑不起来”，而不是“功能正确”。上一版记录里的 34 项全绿，对现在的入口没有任何保护作用。`scripts/evaluate.py` 和 `scripts/audit_delivery.py` 还挂在 `service`、`retrieval` 上，能跑，但测的是老链路，不是线上这一条。

修法有两条，选一条即可：给简版补一个能构造处理器的工厂函数，让老测试至少在接口形状上继续有效；或者把 HTTP 测试改成直接启动简版服务，只保留 `/api/ask`、`/api/health`、同源和长度边界这些当前真正存在的行为。纯检索、引用、超时、密钥脱敏这些用例和 HTTP 层无关，可以留着。

### 问题三：README 和代码对不上

- README 写着“本仓库没有部署工作流，也没有远程发布”，实际仓库里既有 `render.yaml`，也有 `.github/workflows/pages.yml`；
- README 描述了 `/api/ask/stream` 的 NDJSON 过程流和白盒面板，现在的 `web.py` 只有 `/api/ask` 和 `/api/health`；
- README 的 CLI 示例是 `--method vector`、`--retrieve-only`，现在的 `cli.py` 只有 `--answer`。

这类不一致比代码 bug 更费时间，因为照着文档操作会先怀疑环境，再怀疑密钥，最后才发现接口早就不在了。文档和入口一起改，比事后补要省事。

### 部署这一层

前端和后端是分开的，链路很短：

- GitHub Pages 发布 `web/` 目录，就是那个 `index.html`、`app.js`、`styles.css` 和三行 `config.js`；
- 前端把问题 POST 到 `config.js` 里配置的 `RAG_API_BASE`，默认指向 Render 上的后端；
- Render 用 `render.yaml` 启动 `python -m src.web --host 0.0.0.0 --port $PORT`，健康检查走 `/api/health`，`RAG_ALLOWED_ORIGIN` 限制为 `https://wushenghao666.github.io`；
- 密钥只放在 Render 的环境变量里，前端代码和页面里没有任何密钥。

服务启动时会重建索引，所以免费实例重启后不需要额外步骤，代价是冷启动要等一会儿。这次访问后端得到的是 503，正是免费实例休眠后的状态，等它被唤醒才恢复；页面本身是静态的，一直能打开，但这时点“开始”只会看到请求失败。这个体验值得在页面上写一句提示。

在线地址：[最小 RAG 问答页](https://wushenghao666.github.io/ai-learning-week6-rag-langchain/)，后端是 [Render 服务](https://ai-learning-week6-rag-langchain.onrender.com)，代码在[项目仓库](https://github.com/wushenghao666/ai-learning-week6-rag-langchain)。
