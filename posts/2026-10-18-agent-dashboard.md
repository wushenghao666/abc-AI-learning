第四周完成了任务依赖、会话保存、失败重试和复盘指标。那时主要在终端里创建计划、分次执行，再打开 JSON 文件检查状态。第四周博客末尾计划给它加一个 Web 界面，这周就围绕这件事继续做。

## 把 Agent 接到浏览器上

### 项目结构与本地运行

代码放在[第五周项目仓库](https://github.com/wushenghao666/ai-learning-week5-agent-dashboard)，线上入口是[学习计划控制台](https://wushenghao666.github.io/ai-learning-week5-agent-dashboard/)。这周主要新增和调整的文件如下：

```text
ai-learning-week5-agent-dashboard/
├─ src/
│  ├─ agent.py          初始化、执行和复盘
│  ├─ memory.py         会话与事件保存
│  ├─ llm.py            模型请求、校验和重试
│  └─ web.py            HTTP 接口与会话隔离
├─ web/
│  ├─ index.html        控制台和示例说明
│  ├─ app.js            状态展示与过程可视化
│  └─ demo.js           浏览器本地模拟
├─ tests/              单元测试和真实接口检查
├─ render.yaml         后端部署配置
└─ blog/               学习记录副本
```

本地运行命令保持简单：

```powershell
python -m src.web
```

打开 `http://127.0.0.1:8000/` 后就能创建计划。请求处理中禁用操作按钮，服务端通过锁串行处理状态修改，减少重复点击带来的重复执行和文件写入问题。静态文件限制在 `web` 目录内，会话文件与页面资源分开管理。

### 接口与会话状态

后端使用 Python 标准库的 `ThreadingHTTPServer`，接口放在 `src/web.py`。前端使用 HTML、CSS 和 JavaScript，通过 HTTP 请求读取和修改会话。一次操作结束后，服务端返回最新状态，页面据此更新任务卡片、依赖图和指标。

主要接口如下：

| 接口 | 用途 |
| --- | --- |
| GET /api/health | 检查服务和模型配置状态 |
| GET /api/session | 读取当前会话 |
| POST /api/init | 根据目标创建计划 |
| POST /api/run | 执行当前满足依赖的任务 |
| POST /api/reset | 清空当前会话 |

任务的先后关系继续由 `Session.ready_tasks()` 判断。前端只把当前可执行任务显示出来，执行按钮也直接调用现有执行器。完成率和工具成功率来自 `review()`，网页与命令行共用这部分计算。

浏览器用随机会话编号区分各份计划，编号通过 `X-Session-Token` 发送到后端，对应的状态保存在单独的 JSON 文件里。刷新页面后重新读取这份会话，任务结果和调用记录都能恢复。随机编号承担会话隔离，项目目前没有用户登录系统。

## 在页面上查看规划与工具调用

最初的界面主要展示任务和完成率，查看一次规划发生了什么还需要翻文件。后来增加了规划记录，页面可以依次看到输入目标、模型返回的任务草案和校验结果。返回用量数据时，也能展开查看 Token 统计。

执行过程有两种视图。依赖图按 `depends_on` 连线，绿色表示完成，紫色表示可以执行，灰色表示等待，红色表示失败。时间线保存每次工具调用的输入、返回值、尝试次数和耗时，最新调用排在前面。

这些内容都来自实际记录。模型输出未经校验时保留原文，校验失败会留下错误，重新请求也有单独的记录。页面请求期间显示当前操作，收到完整响应后再展示详细轨迹。当前实现采用完整响应，尚未逐字显示生成中的文本。

## 接入并行科技的真实模型

### 调整接口和请求格式

第四周的模型适配器调用 OpenAI Responses API。这周拿到并行科技平台的密钥后，核对文档发现该平台提供兼容 Chat Completions 的调用方式，需要调整地址、请求体和返回文本的读取位置。

适配后的地址为 `https://llmapi.paratera.com/v1/chat/completions`，模型使用账户模型列表中确认过的 `GLM-4-Flash`。请求携带系统指令和用户目标，程序从返回消息中取出文本，再解析任务列表。项目同时保留 Responses 接口，通过环境变量选择调用方式。

密钥放在后端环境变量中，前端只发送目标与模式标记。没有配置密钥时，开启模型选项会得到本地模拟计划，页面显示明确提示。关闭模型选项则使用规则规划。已经配置密钥但请求或校验失败时，页面展示错误及尝试记录，便于检查原因。

### 模型规划与本地工具

模型负责生成任务草案，程序负责检查任务数量、工具名称、参数类型和依赖关系。当前四个工具分别生成目标摘要、行动清单、时间预算和复盘提醒。

这种分工也决定了结果的含义。作品集示例会得到内容整理、页面原型和检查步骤，网站开发仍然要按照清单继续完成。完成率达到 100% 表示这份会话的工具任务执行完毕，实际学习或项目工作需要使用者继续推进。

接入真实模型后，我更清楚地看到了校验的必要性。同一个目标可以返回不同数量的任务，模型还会补充用户没有给出的时间。提示词提供约束，程序继续检查这些约束是否满足，再决定计划能否进入执行阶段。

## 用四个示例检查完整流程

页面放入了四个固定目标，便于重复检查同一套流程：

| 示例 | 输入中的时长 | 时间预算工具结果 |
| --- | --- | --- |
| RAG 学习与检索练习 | 6 小时 | 分为 3 天，每天约 2 小时 |
| 个人作品集网站与页面原型 | 8 小时 | 分为 4 天，每天约 2 小时 |
| 机器学习面试与复习重点 | 4 小时 | 分为 2 天，每天约 2 小时 |
| 本周读书笔记与复盘清单 | 未提供 | 建议先安排每天 1 小时 |

最终版本要求每份模型计划包含四种工具，每种出现一次，详细步骤放在清单里。目标不同，摘要、清单内容和复盘提醒也会变化。这样可以保持页面说明与实际产出一致。

模型任务带有前置依赖，执行器每次处理当前满足条件的任务。在这次线上面试检查中，四个任务按顺序完成，完成率依次显示 25%、50%、75%、100%，最后保留四条工具调用事件。

## 将前端和后端部署到公网

GitHub Pages 提供静态页面，Python 服务运行在 Render 免费实例上。GitHub Actions 发布前端前，根据仓库变量 `AGENT_API_BASE` 生成配置文件，页面再通过这个地址访问后端。后端设置允许的前端来源，处理跨域请求。

真实模型使用的后端配置为：

```text
OPENAI_API_STYLE=chat_completions
OPENAI_BASE_URL=https://llmapi.paratera.com/v1
OPENAI_MODEL=GLM-4-Flash
OPENAI_API_KEY=在 Render 中填写密钥
```

环境变量沿用原适配器的命名，接入平台由地址和接口类型决定。部署后健康接口显示模型已配置，再从前端开启真实模型选项检查规划。

一次线上面试目标测试中，模型响应约 17.3 秒，返回四个任务并通过校验，用量为 389 个输入 Token、275 个输出 Token，共 664 个 Token。四种工具随后全部执行成功，刷新页面后模型记录、任务状态和事件都能恢复。

Render 当前使用临时文件保存会话，实例休眠或重启后记录可能清空。免费服务唤醒也会增加等待时间。项目仍保持这个存储方式，使用时需要留意这两个边界。

## 重复测试中发现的问题

### 任务数量和页面说明对不上

单次面试测试通过后，我又用 API 请求对页面四个目标各测两次。原版本八次请求中有六次完成流程，作品集目标两次均失败。查看原始输出后，发现模型生成了八个任务，超过了当时允许的数量。读书笔记两次请求虽然成功，却都只有两个任务，缺少页面说明中的时间预算和复盘提醒。

于是把计划约束统一为四种工具，要求详细操作集中到清单，同时降低生成温度。校验失败时，将具体错误反馈给模型重新规划，最多请求三次。原始输出、错误和重新请求记录继续保留，工具执行只使用通过校验的计划。

### 读书笔记出现了推测的时长

第二个问题来自读书笔记的时间预算。目标没有给出小时数，模型仍会填入推测的时长。继续让模型重写也出现了同类结果。最终处理方式是保留原始草案，移除这类推测值，记录处理原因，再由时间预算工具显示每天 1 小时的建议。目标明确给出小时数时，校验会要求模型使用相同的总时长。

### 分别处理模型请求和工具执行失败

此外，模型请求增加了有限重试，临时网络错误可以再次尝试，认证失败直接提示。模型规划最多尝试三次，工具执行仍沿用第四周的两次尝试，两类记录分别展示。重试会增加等待和模型用量，页面说明里也补充了这一点。

自动测试使用以下命令：

```powershell

```

结果为 22 项 Python 测试全部通过，浏览器本地模拟的四种场景也通过。新增检查包括超量任务后的错误反馈、错误时长拒绝、未提供时长的处理记录、超时恢复、认证失败停止重试，以及未注册工具拒绝。

真实调用通过 `tests/manual_scenarios.py` 检查。最终版本在本地对四个示例各运行两次，八次全部通过；部署后再次从公网 API 各运行两次，八次也全部通过。公网这八次均在首次规划时通过校验，每次都检查了四种工具、时间预算、完整执行和会话重新读取。

这轮测试修复了已经复现的问题，也留下了可以再次运行的检查脚本。模型输出仍需要逐次校验，外部服务出现异常时，页面会保留错误供检查。
