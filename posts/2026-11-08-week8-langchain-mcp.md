第八周，我把学习重点放在了 **MCP（Model Context Protocol）** 上。此前我已经做过 Agent、工具调用和 RAG，这周我希望搭一条完整链路，弄清楚一个工具怎样通过 MCP 提供出来，又怎样被 Agent 发现和调用。

因此，这周项目的目标很明确：**找一组足够熟悉、能够验证结果的功能，用它们实践 MCP。**

项目已经部署到 Render，可以打开[在线演示](https://week8-mcp-agent.onrender.com/)体验；完整代码保存在 [GitHub 仓库](https://github.com/wushenghao666/week8-mcp-agent)。Render 服务存在冷启动，首次打开或长时间闲置后再次访问时，启动通常需要等待约 30～60 秒。

## MCP 解决什么问题

Agent 要使用外部能力，首先需要知道有哪些工具、每个工具接收什么参数，以及应该怎样发起调用。如果每个工具都有一套不同的接入方法，那么更换 Agent 或增加工具时，就需要反复编写连接代码。

MCP 更像是一套通用插座。工具按照统一格式说明“我叫什么、能做什么、需要什么参数、会返回什么”，客户端则按照同一套规则发现并调用它。它的核心作用是为 **模型应用与外部工具建立标准化连接**。

在这次项目中，可以把几个角色简单理解为：

- **MCP Server** 提供工具，并描述工具的名称、参数和返回结果；
- **MCP Client** 连接 Server，把工具加载到应用中；
- **LangChain Agent** 根据用户的问题决定是否调用工具；
- **模型**理解问题，并把工具返回的内容整理成自然语言回答。

整条链路可以压缩成一句话：

> 用户提问 → LangChain Agent 判断要用什么工具 → 通过 MCP 调用工具 → Agent 把工具结果整理成回答

## 笔记检索和学习规划作为工具

理解了 MCP 的基本角色后，我需要为实践项目选择具体工具。前几周正好已经完成了两类可以复用的功能：第六、七周的笔记检索，以及之前学习 Agent 中的规划逻辑。它们的输入和输出都比较清楚，而且结果容易检查，很适合用来观察 MCP 接入前后发生了什么。

于是，我把它们拆成两个 MCP Server，共提供三个工具：

| 工具 | 能做什么 |
| --- | --- |
| `search_notes` / `list_notes` | 检索前六周的学习笔记，或列出已经导入的资料 |
| `plan_study` | 把一个学习目标拆成任务和时间安排 |

前几周的项目为这次实践提供了基础：第三周的 Agent 按照规则选择工具，第四、五周的模型生成包含工具名称和参数的计划。第八周的重点是 **MCP 的工具提供与连接过程**：把原本由项目内部直接调用的 Python 功能包装成 MCP 工具，再通过 LangChain 的 MCP 客户端交给 Agent。

MCP Server 只执行确定性逻辑。笔记检索沿用关键词与 BM25 排序，学习规划沿用规则。这样的设计把注意力集中在 MCP 链路上；结果异常时，我也能分别检查原有函数、MCP 调用和 Agent 的工具选择。

## Agent 的角色

接入 MCP 后，Agent 扮演调度员的角色，负责判断任务并选择合适的工具。

比如我问：

- “第六周的 RAG 项目是怎么切分资料的？”——它应该先搜索学习笔记；
- “我想用两小时复习 MCP，怎么安排？”——它应该调用学习规划工具；
- “先回顾 RAG，再帮我安排下一步”——它可能需要连续调用两个工具。

模型负责理解问题、选择工具和整理结果；我的学习记录由检索工具提供，规划结果由规划工具生成。

三者的分工清晰：Agent 负责决定下一步，MCP 负责连接，工具负责执行具体任务。

我先把前六周的博客和 README 导入本地资料库，共 12 份快照；然后给检索和规划代码包上一层 MCP 接口；最后用 `langchain-mcp-adapters` 把这些工具交给 LangChain Agent。模型通过兼容 OpenAI 接口的 `ChatOpenAI` 接入，密钥保存在后端环境变量中。

本地默认使用 `stdio` 连接：Agent 启动 MCP Server 子进程，通过本地管道通信，工具只在本机使用。项目也保留了 `memory` 模式，适合在同一进程内建立 MCP 会话。

网页端也尽量把 Agent 的工作过程展示出来。提问后，页面会显示正在调用哪个工具、工具何时返回，并逐步输出最终答案。完整的调用过程可以帮助我检查工具选择和回答依据。

## 遇到的问题

开发中最典型的问题出现在流式回答上。

最初，每收到一次网页请求，都会临时创建一个异步事件循环，请求结束后再关闭。单次看似正常，但连接池可能在下一次请求里复用之前的连接，而那条连接还绑定在已经关闭的循环上，于是程序会间歇性报出 `Event loop is closed`。它甚至会出现“一次成功、一次失败”的现象，很难第一眼定位。

最后的处理方式是：服务启动时在后台线程中创建一个常驻事件循环，后续请求都提交到这个循环执行，每次请求共享同一个循环。

## 小结

Agent 系统可以拆成几个边界清楚的部分：

- **模型**负责理解意图和组织语言；
- **LangChain Agent**负责对话流程与工具选择；
- **MCP**负责用统一方式连接工具；
- **工具**负责检索、规划等可以验证的具体工作；
- **网页**负责展示回答，也展示工具调用过程。

项目目前保持了较小的范围：检索采用关键词 BM25，规划采用规则，`stdio` 模式下每次请求都会重新创建 MCP 客户端。这套实现适合本地演示，也让我把注意力集中在 MCP 的核心结构上。

项目保留了 29 个测试，覆盖分词、切分、检索、规划、工具注册以及通过 MCP 协议调用工具。测试既验证函数本身，也验证工具通过协议调用后能返回正确结果。

第八周让我完整实践了 MCP 的工具提供、连接和调用过程，也把过去几周完成的功能接入了同一个 Agent。
