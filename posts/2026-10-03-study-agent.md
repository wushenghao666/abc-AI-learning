## 本周目标

前两周我一直在做分类模型：第一周跑通 MLP 的训练闭环，第二周比较 CNN、数据增强和混淆矩阵。这周我把学习方向提前转到 Agent。这周先做一个小型 Agent，用代码观察它如何理解目标、安排步骤和调用工具。

本周我实现了一个学习计划 Agent。它接收一句自然语言目标，把目标拆成几个步骤，根据步骤选择本地工具执行，把每一步的输入、输出和状态记录下来，最后生成一份可以复盘的报告。项目仓库是 [ai-learning-week3-study-agent](https://github.com/wushenghao666/ai-learning-week3-study-agent)，代码和本博客副本放在同一个仓库中。

## 学习内容：Agent 到底是什么

### 从一次回答到一个闭环

普通的函数通常是固定的：传入参数，执行预先写好的逻辑，再返回结果。例如 `calculate(12 / 3)` 只负责计算。Agent 还要根据目标决定下一步行动。它接收目标，再选择要调用的函数；它需要先理解目标、制定计划，再选择工具，把工具结果带回流程中。

我把本周接触到的 Agent 抽象成下面这条链路：

```text
目标（Goal）
  ↓
观察与理解（Understand）
  ↓
规划（Plan）
  ↓
行动：调用工具（Act）
  ↓
读取结果并更新状态（Observe）
  ↓
继续行动或输出答案（Report）
```

这条链路描述程序如何组织模型、工具和状态。在工程实现中，每一步都应该尽量有边界、有记录、可测试。模型可以帮助产生计划或参数，但工具真正执行什么，仍然需要程序定义清楚。

### Agent 的几个组成部分

**目标和状态**是起点。目标描述用户想完成什么，状态则保存已经完成了哪些步骤、工具返回了什么以及是否出错。如果没有状态，Agent 很难知道自己处于哪一步，也无法解释最后的答案是怎么来的。

**规划器（Planner）**负责把大目标变成更小的动作。规划可以由规则、有限状态机或大语言模型完成。本周先用规则实现，把规划过程直接写进代码。以后换成 LLM 时，只需要替换规划器，并保留工具和记录机制。

**工具（Tool）**是 Agent 能够真正做事的接口。工具应该有清晰的名称、输入格式和输出结果，例如计算器接收算式、摘要工具接收一段文字。工具把有限能力包装成可调用函数，并通过参数约束调用范围。工具越少、边界越清楚，越容易测试和控制风险。

**执行器（Executor）**按照计划调用工具，并捕获异常。Agent 运行时需要记录工具失败原因，并决定重试、跳过或请求人工处理。

**记忆（Memory）**可以分成短期和长期。短期记忆是当前任务的对话、计划和工具结果；长期记忆则可能是数据库、向量索引或用户偏好。本周只实现单次运行的短期记忆，不接入向量数据库，避免在还没有理解基本闭环时引入额外复杂度。

### Agent、工作流和聊天机器人的区别

三者经常被混在一起。聊天机器人主要负责多轮对话，工作流是人提前写好的固定步骤，而 Agent 的关键特征是根据目标和中间结果选择下一步行动。固定的先查天气再套模板属于工作流。系统根据用户目标决定是否调用天气工具，并根据结果调整后续回答时，才体现 Agent 的行为。

这个区别对学习很有帮助：不能因为代码里出现了一个 `while` 循环，就把程序叫作 Agent。真正值得观察的是，下一步是否由当前状态和目标共同决定，工具结果是否影响了后面的动作，以及过程能不能被检查。

### 为什么要先做小 Agent

接入大模型 API 很容易让项目看起来很智能，但也会把问题混在一起：提示词写得好不好、模型是否稳定、网络是否可用、费用如何控制，都可能掩盖 Agent 本身的结构。先用规则规划器做一个离线版本，可以把目标、计划、工具、状态和报告拆开验证。等这些接口稳定后，再逐步加入真实模型，比较规则规划和模型规划带来的差异。

## 项目实践：学习计划 Agent

### 需求和边界

我给本周项目设定了四个小目标：输入一句学习目标；生成不超过四步的计划；至少支持计算、摘要和清单三个工具；保存可读的执行轨迹。项目不联网、不执行任意 shell 命令、不修改用户文件，也不要求 API key。这样的边界让示例可以离线复现，同时把后续扩展点留出来。

项目结构如下：

```text
src/
├─ agent.py       # Planner、StudyAgent 和命令行入口
├─ tools.py       # calculator、summarize、checklist
└─ memory.py      # Event 和 Memory
 tests/test_agent.py
 examples/tasks.json
```

### 规划：从文字中提取行动

`Planner.plan()` 是当前版本的大脑。它用少量规则识别 agent、智能体、小时、计算、总结等关键词。如果目标包含学习 agent，就加入理解核心概念、完成最小实现、运行测试并复盘三个步骤；如果目标出现算式，就追加计算步骤；如果出现时长，就先把约束记录下来。

```python
steps = Planner().plan('我想学习 agent，并安排 6 小时复习时间')
```

这个规划器只覆盖有限的中文表达，也不处理复杂上下文。计划在这里是独立阶段，并保存为结构化的 `Step(title, action, tool, argument)` 对象，后续执行可以直接读取这些字段。

### 工具：把能力放在受控接口里

本项目注册了三个本地工具。`calculate()` 使用 Python 的 AST 解析，只允许数字和基础算术运算，不直接使用 `eval()`；`summarize()` 清理空白并提取第一句话；`checklist()` 把字符串列表格式化成编号清单。工具函数本身不负责决定什么时候调用，决定权留在规划器和 Agent 循环里。

工具调用过程会生成一条事件：

```python
Event(
    kind='tool_call',
    name='calculator',
    input='12 / 3',
    output='4',
    status='ok',
)
```

有了这条记录，就能看到调用的工具、传入的参数和返回的结果。如果工具报错，事件会保存 `status='error'` 和错误文字，报告仍然能够生成。这比只打印最后一句答案更适合学习和调试。

### 执行循环和短期记忆

`StudyAgent.run()` 先校验目标，再调用规划器，接着逐步执行计划。每一步都从工具注册表中取出函数，执行后把结果同时写入 `results` 和 `Memory.events`。最后返回一个字典，其中包括原始目标、结构化计划、结果列表和完整记忆。

```text
run(goal)
  ├─ plan = planner.plan(goal)
  ├─ for step in plan:
  │    ├─ call tool(step.tool, step.argument)
  │    └─ memory.record(event)
  └─ return report
```

这里的记忆只存在于当前进程，程序关闭后历史记录会清空。它的价值在于让当前运行可观察、可测试，也为以后换成 JSON 文件或数据库提供了稳定的数据结构。

### 命令行运行示例

在项目目录中运行：

```powershell
python -m src.agent '我想在本周学习 agent，并安排 6 小时复习时间'
```

输出会列出每一步使用的工具和结果。要查看机器更容易处理的完整轨迹，可以加 `--json`：

```powershell
python -m src.agent '比较 12 / 3 和 5 * 8，并整理成检查清单' --json
```

测试则使用 Python 标准库：

```powershell
python -m unittest discover -s tests -v
```

测试覆盖计算器结果、摘要截断、Agent 选择多个工具、记忆事件数量和空目标错误处理，先固定本周关注的结构。

### 运行结果和观察

输入带有学习主题和时长的目标时，规划器会先记录时间约束，再生成学习概念、最小实现和复盘步骤。输入带算式的目标时，执行轨迹中会出现计算器调用；输入总结或整理时，会出现摘要工具。当前 Agent 已经具备目标 → 计划 → 工具 → 记忆 → 报告的完整路径。

同时也能看到规则方案的局限：关键词稍微变化，规划结果就可能不理想；摘要只取第一句话，不能判断事实是否重要；Agent 不会自己验证计划是否真的完成。下一步接入 LLM 时，最需要保留的是结构化步骤和工具白名单，同时保留工具白名单，把判断范围控制在可检查的步骤内。

## 本周真正理解了什么

这周我把 Agent 拆成了可以运行的部件。Agent 围绕目标规划步骤，调用有限工具，读取中间结果，再继续执行。规则版本的每个环节都能直接查看，方便理解各部分的责任。

后续我会在这个项目上逐步加入真实模型调用、结构化输出校验、文件工具和人工确认，并设计几组固定任务来评估规划是否稳定。本周先停在一个可离线复现的最小版本：它足够说明 Agent 的基本闭环，也给后面的扩展留下了清楚的接口。
